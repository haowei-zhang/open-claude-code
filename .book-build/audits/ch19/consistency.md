# Consistency Audit: Chapter 19 — Sync vs Fork vs Remote: The Execution Modes

## Term Conflicts

1. **"subagent" vs "sub-agent"**: The terminology registry defines "subagent" (one word). The chapter uses both "subagent" and "sub-agent" inconsistently. In the forkSubagent.ts snippet references, "sub-agent" appears in rule 1 of buildChildMessage ("Do NOT spawn sub-agents"). The Overview and Data structures sections consistently use "subagent". However, the buildChildMessage snippet itself contains "sub-agents" which is the actual source code text, not the chapter's own prose. In the chapter's own prose, "subagent" is used consistently. **No prose conflict**, but the quoted source code uses the alternate form.

2. **"fork"**: The terminology registry defines "fork" as "A child process created via Bun.fork()". The chapter uses "fork" consistently with this definition. No conflict.

3. **"task"**: The terminology registry defines "task" as a durable unit of work. The chapter uses "task" consistently in the context of LocalAgentTaskState and RemoteAgentTaskState. No conflict.

4. **"feature gate"**: The terminology registry defines "feature gate" as a compile-time boundary. The chapter references the FORK_SUBAGENT feature flag in the context of isForkSubagentEnabled(). The chapter says "The fork path is gated by the `isForkSubagentEnabled()` function, which checks three conditions: the `FORK_SUBAGENT` feature flag is on". This is consistent with the registry definition.

5. **"dispatch pipeline"**: The registry defines "dispatch pipeline" as the ordered sequence of stages. The chapter mentions "the dispatch falls back to local execution" which is a different usage — it refers to the dispatch decision, not the pipeline. This is acceptable usage.

6. **"auto-background"**: The registry defines "auto-background" as the mechanism that transitions sync to async after 120s. The chapter references this correctly: "Sync agents can be automatically promoted to async after 120 seconds."

7. **"fork recursion guard"**: The registry defines this term. The chapter references the mechanism (isInForkChild) but doesn't use the term "fork recursion guard" by name. This is acceptable — the concept is covered.

8. **"cache boundary" / "prompt cache"**: The chapter references "prompt cache" extensively. This is consistent with the registry's "cache boundary" definition context.

## Voice Drift

The chapter is written in present tense, descriptive style, with heavy citation of source files and line numbers. This is consistent with the house style ("present tense, descriptive, cite-heavy"). No voice drift detected.

## Proposed New Terms

1. **"cache-safe params"** — The CacheSafeParams type and the pattern of capturing byte-identical API request parameters for prompt cache sharing across fork children. Definition: "A set of API request parameters (system prompt, tools, model, context messages) captured immediately after assembly to ensure byte-identical prefixes between parent and fork children for prompt cache hits."

2. **"placeholder tool_result"** — The pattern of inserting identical synthetic tool_result blocks for all tool_use blocks in the parent's assistant message, ensuring that fork children share the same prompt cache entry for the shared prefix. Definition: "A synthetic tool_result block with identical placeholder text (FORK_PLACEHOLDER_RESULT) inserted for every tool_use block in the parent's assistant message, ensuring all fork children produce byte-identical API request prefixes up to the per-child directive."

3. **"bubble permission model"** — The pattern where fork children route permission prompts to the parent terminal via IPC since they have no terminal of their own. Definition: "A permission model where fork child processes route permission requests to the parent's terminal via IPC, since the child process has no terminal of its own, controlled by permissionMode: 'bubble' on the agent definition."

4. **"fork boilerplate"** — The strict XML-tagged instruction block injected into fork children that prevents recursive forking and enforces a machine-parseable output format. Definition: "An XML-tagged instruction block wrapped in FORK_BOILERPLATE_TAG that is injected into fork child messages to prevent recursive forking, enforce structured output format, and constrain the child's behavior to its directive scope."

5. **"worktree path notice"** — The advisory message injected into fork children running in isolated worktrees about translating file paths from the parent's working directory. Definition: "An advisory message generated by buildWorktreeNotice() that warns fork children running in isolated worktrees to translate inherited context paths from the parent's working directory to the worktree root."
