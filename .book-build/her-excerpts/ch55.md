## §21 Reference Architecture

## 21. Reference Architecture for a Production Harness (Aspirational)

**IMPORTANT**: This architecture is synthesized from multiple sources that each solve different problems. **No public implementation covers all eight layers.** The celesteanders/harness repo (cited as a reference implementation) implements only Layers 1-2 and part of Layer 4. Combining patterns into one stack does not mean the combination has been validated. Treat this as a reference for what a comprehensive system *could* look like, not as a proven blueprint.

### Layer 1: Task Infrastructure
- JSON task list (append-only, boolean pass/fail)
- Task decomposition into session-sized units (15-30 min target)
- Priority ordering and dependency tracking
- Immutable task descriptions, mutable status only

### Layer 2: Session Management
- Session startup protocol (orient -> setup -> verify -> select)
- Clean exit protocol (update state -> commit -> persist notes)
- Session-to-session handoff via structured files
- Maximum session duration limits with graceful wind-down

### Layer 3: Context Engineering
- Progressive compaction at token thresholds
- Observation masking (suppress successful outputs)
- Tiered memory (always-loaded index + on-demand topic files)
- Sub-agent isolation for research/exploration
- Context reset with structured handoff when degradation detected

### Layer 4: Quality Gates (Back-Pressure)
- Pre-commit: type-check, lint, format
- Post-commit: unit tests, integration tests
- Per-feature: E2E browser automation
- Per-session: evaluator agent in fresh context
- Success is silent; only failures produce verbose output

### Layer 5: Safety and Security Infrastructure
- Permission tiers (read-only -> discuss -> full access)
- Destructive operation confirmation
- File protection rules
- Loop detection and maximum retry limits
- Rate limiting on tool usage
- Input sanitization for prompt injection
- Idempotency keys for external operations
- Checkpoint-restore safety (ACRFence principles)

### Layer 6: Cost and Observability
- Per-session and per-task cost caps
- Real-time token metering and anomaly detection
- Distributed tracing (OpenTelemetry) across multi-agent workflows
- Structured logging of agent decisions and tool calls
- Dashboard for multi-hour session monitoring
- Alerting on degradation patterns (loop detection, context rot, cost spikes)

### Layer 7: Multi-Agent Coordination
- Generator-Evaluator pattern for quality-critical work
- Model routing (expensive for planning, cheap for execution)
- File-based inter-agent communication
- Git-based conflict resolution
- Isolated worktrees for parallel agent work
- Human-in-the-loop escalation paths

### Layer 8: Learning and Adaptation
- Progress notes persisted to files (survive context resets)
- Pattern discovery logged to AGENTS.md
- Feedback from evaluator recorded for future sessions
- Stale assumptions pruned as models improve
- Harness configuration versioning and A/B testing (Meta-Harness approach)

## §20 20 Best Practices

## 20. Synthesized Best Practices

### The 12 Core Principles

Synthesized from the four canonical sources, academic research, practitioner data, and honest failure analysis:

1. **Context windows are the constraint; structured artifacts are the solution.** Task lists (JSON, not Markdown), progress notes, and git history bridge sessions. If it's not in the repo, it doesn't exist for the agent.

2. **Separate generation from evaluation.** Agents are reliably bad at grading their own work. A standalone skeptical evaluator is far easier to tune than making a generator self-critical. But be aware of the Ouroboros problem -- deterministic evaluation (tests, linters) is more reliable than LLM evaluation.

3. **One task per session.** This single rule prevents more failures than almost anything else.

4. **Verify before building.** Always run a baseline check at session start. Compounding bugs across sessions is one of the most common failure modes.

5. **Wire in fast feedback loops.** Tests, linters, type checkers, and UI automation provide deterministic back-pressure that catches errors the agent won't notice.

6. **Repository is single source of truth.** All state must be persisted to files and git. Context windows are ephemeral; the repo is permanent.

7. **Humans steer, agents execute.** Senior expertise in task selection, architecture decisions, and quality judgment remains essential. The harness amplifies human judgment, not replaces it. Design explicit human-in-the-loop checkpoints for multi-hour tasks.

8. **Expect eventual consistency.** Most issues resolve through more loops with better prompts. The speed of the loop matters more than perfection in any single iteration.

9. **Simplify relentlessly.** Strip unneeded harness complexity as models improve. Every component encodes an assumption about model limitations -- these go stale fast.

10. **Control costs actively.** Set per-session and per-task cost caps. Monitor spend rate in real-time. Budget for 3-10x the happy-path cost. Runaway spending is the #1 operational risk for multi-hour tasks.

11. **Observe everything.** If you can't see what the agent is doing, you can't fix it when it goes wrong. Traces, metrics, and structured logs are table stakes for production use.

12. **Secure by default.** Treat all external content as untrusted. Use least-privilege permissions. Require idempotency for external operations. The agent has the same attack surface as a remote code execution endpoint -- because that's what it is.

### The Session Protocol (Universal)

```
ORIENT  -> SETUP -> VERIFY -> SELECT -> IMPLEMENT -> TEST -> UPDATE -> EXIT
```

### The Back-Pressure Stack

```
Type System -> Linter -> Unit Tests -> Integration Tests -> E2E/Browser Tests
     ^                                                            |
     |                                                            |
     +---- Only failures surface to agent context ----------------+
```

## §19 Decision Framework

## 19. Decision Framework

The report presents patterns descriptively but practitioners need guidance on when to use what. This decision framework maps situations to recommended approaches.

### 19.1 Choosing a Harness Approach

```
Is the task a single, well-defined operation?
├── YES → No harness needed. Direct prompt.
└── NO → Does the task span multiple sessions?
    ├── NO → Simple harness: structured prompt + back-pressure (tests/lints)
    └── YES → Does the task require quality guarantees?
        ├── NO → Ralph-style bash loop (cheap, fast iteration)
        └── YES → Generator-Evaluator pattern
            └── Does it require multiple concurrent agents?
                ├── NO → Single generator + single evaluator
                └── YES → Full orchestration (LangGraph, etc.)
```

### 19.2 Choosing State Management

| Scenario | Recommended Approach |
|----------|---------------------|
| Single session, no handoffs | Context window only (no file state) |
| Multi-session, single agent | Three-file pattern (tasks.json + progress.txt + AGENTS.md) |
| Multi-agent, shared state | File-based communication + git-based conflict resolution |
| Enterprise, distributed | LangGraph with DynamoDB/Redis persistence + event sourcing |

### 19.3 Choosing an Evaluation Strategy

| Quality Need | Strategy |
|-------------|----------|
| Correctness only | Deterministic: tests + linters + type checkers |
| Correctness + design quality | Deterministic + LLM evaluator (fresh context, specific criteria) |
| High-stakes (production, security) | Deterministic + LLM evaluator + mandatory human review |

### 19.4 Choosing Model Routing

| Sub-task | Recommended Model Tier |
|----------|----------------------|
| Planning, architecture decisions | Expensive (Opus-class) |
| Code generation, standard implementation | Mid-tier (Sonnet-class) |
| Summarization, classification, compression | Cheap (Haiku-class) |
| Evaluation / quality judgment | Same tier as generator, or one tier higher |
