## §11 Human-in-the-Loop affordances

## 11. Human-in-the-Loop Design Patterns

The canonical sources state "Humans steer, agents execute" but rarely detail the specific patterns for how humans participate in agent workflows. For multi-hour tasks, these patterns are essential.

### 11.1 Confidence-Based Routing
- **Above threshold** (e.g., 90% confidence): Agent proceeds autonomously
- **Below threshold**: Agent queues the decision for human approval, continues with other work
- **Implementation**: The agent reports its confidence and reasoning; a routing layer (which can be deterministic or model-based) decides whether to proceed or escalate

### 11.2 Tiered Escalation
- **Tier 1** (automated): Deterministic checks handle (linting, testing, formatting)
- **Tier 2** (agent self-correction): Agent gets feedback from Tier 1 and tries again
- **Tier 3** (human front-line): Moderate-risk decisions (e.g., "should I refactor this module?")
- **Tier 4** (human expert): High-risk decisions (architecture changes, security-sensitive operations, production deployments)

### 11.3 Async Approval
- Agent parks a blocked action, records context about what it tried and why it's uncertain
- Agent continues with non-blocked work
- When human approves/denies, agent resumes the blocked work path
- **Critical for multi-hour tasks**: The agent should never fully block on human input. Always have a queue of independent tasks to work on while waiting.

### 11.4 Context-Rich Escalation
When the agent escalates to a human, it must provide:
- What it was trying to do
- What it tried
- Why it failed or is uncertain
- What options it sees
- What it recommends (if it has a preference)

This prevents the human from having to reconstruct full context from scratch.

### 11.5 Handoff Protocols
- **Full context transfer**: Agent writes a structured handoff document summarizing current state, what's done, what's remaining, and any open questions
- **Incremental review**: Human reviews completed chunks (e.g., every 3 tasks) rather than waiting for the end
- **Checkpoint review**: Mandatory human review at 25% and 75% of task completion to catch goal misinterpretation early

## §18 Over-trust risk

## 18. Limitations, Skeptical Perspectives, and When NOT to Use

### 18.1 Is This Just DevOps Rebranded?

Muhammad Raza maps harness components directly to DevOps equivalents. The mapping is instructive:

| Harness Concept | DevOps Equivalent |
|----------------|-------------------|
| Execution environments | CI job runners (Docker, Firecracker) |
| Tool definitions | API design and permission scoping |
| Control loops | Health checks, deployment rollback |
| Guardrails | IAM policies, network rules, resource quotas |
| Observability | Structured logging, request tracing |
| Session management | Container lifecycle management |

**Assessment**: Harness engineering IS substantially DevOps applied to a new workload type. The core innovation is the *probabilistic* nature of the workload -- DevOps orchestrates deterministic processes, while harness engineering orchestrates a non-deterministic process (the LLM) that requires fundamentally different error handling (retry-and-hope rather than fix-the-bug). But the infrastructure patterns, the feedback loops, the observability requirements, and the cost management challenges are deeply familiar to anyone who's run production infrastructure.

Practitioners with DevOps backgrounds should recognize that their skills transfer directly. The discipline is not as novel as some framing suggests.

### 18.2 The Ouroboros Problem

When both generator and evaluator are LLMs, who validates the validator? The report recommends Generator-Evaluator as "the most universally recommended pattern" (Section 9.2), and it is -- but its limitations must be understood:

- An LLM evaluator can hallucinate approval just as easily as a generator can hallucinate success
- The NLAH paper's verifier ablation (-0.8% on SWE-bench) shows this is not theoretical
- **The strongest evaluators are deterministic** (test suites, type checkers, linters) -- use LLM evaluation only for judgments that deterministic tools cannot make

### 18.3 The "Stone Soup" Attribution Problem

Benjamin Riley (citing Alison Gopnik) raises a challenge: in agentic systems, massive human labor (writing specs, designing harnesses, monitoring output, fixing errors) gets misattributed to AI capability. OpenAI's "~1M lines, zero manually written" is technically true but obscures the human engineering effort that made it possible. Huntley's own caveat -- "There is no way this is possible without senior expertise guiding Ralph" -- is the honest version.

### 18.4 Limited Applicability Beyond Coding

Coding is the ideal domain for harness engineering because of the deterministic-probabilistic pairing: write code (probabilistic), run compiler/tests (deterministic), iterate. Most human activities don't have this structure. The patterns in this report should not be assumed to generalize to domains lacking strong deterministic verification (creative writing, strategic planning, research synthesis).

### 18.5 Greenfield Bias

Huntley explicitly states: "There's no way in heck would I use Ralph in an existing code base." Many of the report's most impressive results (OpenAI's ~1M lines, Huntley's $297 contract) are greenfield projects. For brownfield (existing codebase) work:
- The agent must understand existing architecture it didn't create
- Tests may be incomplete or absent, removing a key feedback mechanism
- Modifications must respect implicit conventions not captured in any document
- The risk of breaking existing functionality is much higher

### 18.6 When NOT to Use Harness Engineering

- **Simple one-shot tasks**: If the task fits in a single prompt/response, a harness adds overhead without benefit
- **Domains without deterministic verification**: If you can't automatically check the output, the feedback loop collapses and you're just running an LLM with extra steps
- **When human review is faster**: For tasks requiring deep domain expertise and judgment, the overhead of specifying, monitoring, and correcting an agent may exceed the cost of doing it manually
- **Security-critical operations without proper isolation**: If you cannot sandbox the agent's tool access, the risk of unintended side effects may outweigh the productivity gain
- **When the codebase has low harnessability** (per Fowler): Weakly-typed, poorly-structured legacy code with no tests is simultaneously where a harness is most needed and hardest to build

### 18.7 The Scale Confusion

The literature conflates harnesses operating at very different scales:

| Approach | Complexity | Best For |
|----------|-----------|----------|
| Ralph/bash loop | ~10 lines | Single developer, greenfield, rapid iteration |
| Generator-Evaluator | ~100s of lines | Quality-critical features, multi-session work |
| Full orchestration (LangGraph, etc.) | ~1000s of lines | Enterprise, multi-agent, production systems |
| 8-layer reference architecture | Aspirational | No public implementation covers all 8 layers |

These are qualitatively different systems, not points on a single continuum. Choose the simplest approach that meets your actual needs. Simon Willison's observation that a coding agent is fundamentally "a few dozen lines of code" is a useful reminder that complexity should be earned, not assumed.
