# HER Excerpt for Chapter 18

## From §7.4: Sub-Agents as a Configuration Surface

- Discrete tasks in isolated context windows
- Use expensive models (Opus) for parent orchestration
- Use cheaper models (Sonnet, Haiku) for sub-tasks
- Primary benefit: prevents research/exploration from consuming the main context window

Sub-agents are not just an execution mechanism -- they are a configuration surface. The decision of what tasks to delegate to sub-agents, what models to use for each, and what permissions to grant them constitutes a critical harness configuration. Key design decisions:

- **Model selection per sub-agent**: Expensive models for planning and evaluation; cheap models for implementation and summarization.
- **Permission scoping**: Research sub-agents should be read-only; implementation sub-agents need write access but only to specific directories.
- **Context isolation**: Each sub-agent operates in its own context window, preventing the parent's context from being consumed by detailed research or exploration.
- **Result aggregation**: The parent agent receives only summaries or structured findings from sub-agents, not the full context of their work.

## From §5: Pattern 7 Context-Isolated Subagents

7. **Context-Isolated Subagents**: Separate context windows per phase; research agents cannot edit

This pattern enforces strict context isolation between sub-agents. Each sub-agent operates in its own context window with its own permissions, preventing cross-contamination. The most important constraint: research/exploration agents cannot edit files. This prevents the common failure mode where an agent, while researching, starts making premature changes before fully understanding the problem.

**Key benefits**:
- **Context preservation**: The parent agent's context window is not consumed by detailed research or exploration.
- **Permission enforcement**: Read-only research agents physically cannot make changes, preventing premature action.
- **Clean handoffs**: Sub-agents return structured findings, not unstructured context that the parent must parse.
- **Cost optimization**: Cheap models can handle research while expensive models are reserved for planning and evaluation.

## From §5: Pattern 8 Fork-Join Parallelism

8. **Fork-Join Parallelism**: Multiple subagents in isolated git worktrees; cached parent context reuse

This pattern enables parallel execution by spawning multiple sub-agents, each working in its own isolated git worktree. The "fork" creates independent working copies; the "join" merges the results back into the main branch.

**Key design elements**:
- **Isolated worktrees**: Each sub-agent works in its own git worktree, preventing file conflicts between parallel agents.
- **Cached parent context**: Sub-agents receive a snapshot of the parent's context at fork time, avoiding the cost of re-assembling context for each agent.
- **Merge coordination**: The join phase must handle potential conflicts when multiple agents modify the same files. Git-based conflict resolution provides a natural mechanism.
- **Resource limits**: Unlimited subagents can exhaust system resources. Limits on concurrent agents and total agent count are essential.
