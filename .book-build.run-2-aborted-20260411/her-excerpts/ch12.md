# HER Excerpt for Chapter 12

## From §5: Pattern 12 Deterministic Lifecycle Hooks

12. **Deterministic Lifecycle Hooks**: Shell commands at 25+ lifecycle points (PreToolUse, PostToolUse, SessionStart, etc.)

This pattern provides deterministic, user-defined shell commands that execute at specific points in the agent's lifecycle. Unlike model-generated actions, lifecycle hooks are deterministic -- they always execute the same way regardless of model behavior. This makes them the most reliable mechanism for enforcing harness constraints.

**Key lifecycle points**:
- **SessionStart**: Run initialization scripts, verify environment
- **PreToolUse**: Validate tool parameters before execution, enforce file protection rules
- **PostToolUse**: Auto-format after edits, verify changes meet quality standards
- **Stop**: Prevent premature completion, enforce exit protocols
- **TaskCompleted**: Run quality gates before declaring work done

**Common patterns**:
- Auto-format after file edits (PostToolUse)
- File protection via PreToolUse (prevent modifications to critical files)
- Premature-completion prevention via Stop hooks (verify task completion criteria)
- Quality gates via TaskCompleted hooks (run tests before accepting work)

**Key insight**: Lifecycle hooks encode assumptions about model limitations in deterministic code. They are the most reliable mechanism in the harness because they do not depend on model cooperation. The model cannot bypass a PreToolUse hook; it executes regardless of what the model intends.

## From §6.8: Tool Explosion

- **Symptom**: Too many tools degrade selection accuracy
- **Fix**: Progressive tool expansion starting with <20

When the agent has too many tools available simultaneously, it struggles to select the correct one. The tool descriptions compete for attention in the context window, and the model's ability to discriminate between similar tools degrades as the number grows. This is sometimes called entering "the dumb zone" -- the model has so many options that it makes worse choices than it would with fewer, more focused tools.

The fix is progressive tool expansion: start with a small set of essential tools (typically under 20), and activate additional tools only when contextually needed. This keeps the tool selection problem tractable while still providing access to specialized capabilities when required.

## From §6.6: Silent Failures

- **Symptom**: Agent proceeds after tool errors as if successful
- **Fix**: Structured output validation after every tool call

Silent failures are among the most dangerous failure modes because they are invisible. The agent calls a tool, the tool returns an error (or a result that doesn't match the expected outcome), and the agent interprets this as success. It then proceeds to build on a foundation of failed operations, compounding errors with each subsequent step.

The fix requires structured output validation after every tool call. The harness must verify that the tool's output meets the expected schema and that the operation actually achieved its intended effect. A 200 OK from a tool call doesn't mean the operation succeeded semantically. This connects directly to the "Observability Gap" (Section 14.2) -- observability must go beyond "did the API call return?" to "did the operation achieve its intended effect?"
