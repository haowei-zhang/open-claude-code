# HER Excerpt for Chapter 13

## From §5: Pattern 11 Single-Purpose Tool Design

11. **Single-Purpose Tool Design**: FileReadTool, FileEditTool, GrepTool each with individual permission rules

This pattern advocates for designing tools that do exactly one thing, with a clear and narrow scope. Rather than a single "FileTool" that can read, write, search, and modify files, the harness provides separate tools for each operation. Key benefits include fine-grained permission control, clearer model behavior, easier security auditing, and reduced tool description complexity.

## From §6.4: Placeholder Implementations

- **Symptom**: Agents default to stubs because compiling triggers reward signals
- **Fix**: Explicit anti-placeholder instructions ("DO NOT IMPLEMENT PLACEHOLDER OR SIMPLE IMPLEMENTATIONS")

Placeholder implementations are a particularly insidious failure mode because the agent believes it has made progress. The agent writes a stub function that compiles and passes basic type checking, generating a "success" reward signal. But the stub contains no actual logic -- it's just a shell that satisfies the compiler. The agent moves on, satisfied, while the actual functionality is missing.

Geoffrey Huntley's Ralph approach includes the forceful instruction: "DO NOT IMPLEMENT PLACEHOLDER OR SIMPLE IMPLEMENTATIONS. WE WANT FULL IMPLEMENTATIONS." This explicit anti-placeholder directive is necessary because the model's default behavior, shaped by training data that includes many stub implementations, is to write minimal code that satisfies immediate constraints.

## From §6.15: Data Leakage Between Contexts

- **Symptom**: Information leaks between sessions, between sub-agents, or through file-based communication.
- **Evidence**: File-based communication (recommended in Section 9.3) inherently persists data to disk. Without cleanup, sensitive data from one task context can bleed into another.
- **Fix**: Context isolation via separate file namespaces; cleanup protocols; avoid logging sensitive data in progress files; use ephemeral directories for sensitive work.

Data leakage between contexts is a subtle but serious concern in multi-session and multi-agent systems. The very mechanisms that enable session continuity (progress files, task lists, git history) also create opportunities for information to flow between unrelated tasks. A progress file from a security-sensitive task may contain credentials or API keys that a subsequent session on an unrelated task could access. File-based communication between agents (Section 9.3) is recommended for context fidelity, but it inherently persists data to disk where it can be read by any subsequent process.
