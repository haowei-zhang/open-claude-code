## 18. Limitations, Skeptical Perspectives, and When NOT to Use

### 18.1 Is This Just DevOps Rebranded?

Muhammad Raza maps harness components directly to DevOps equivalents. The mapping is instructive:

| Harness Concept | DevOps Equivalent |
|----------------|-------------------|
| Execution environments | CI job runners (Docker, Firecracker) |
| Tool definitions | API design and permission scoping |
| Control loops | Health checks, deployment rollback |
| Guardrails | IAM policies, network rules, resource quotas |
| Observability | Structured logging, request tracing |
| Session management | Container lifecycle management |

**Assessment**: Harness engineering IS substantially DevOps applied to a new workload type. The core innovation is the *probabilistic* nature of the workload -- DevOps orchestrates deterministic processes, while harness engineering orchestrates a non-deterministic process (the LLM) that requires fundamentally different error handling (retry-and-hope rather than fix-the-bug).

### 18.2 The Ouroboros Problem

When both generator and evaluator are LLMs, who validates the validator?
- An LLM evaluator can hallucinate approval just as easily as a generator can hallucinate success
- The NLAH paper's verifier ablation (-0.8% on SWE-bench) shows this is not theoretical
- **The strongest evaluators are deterministic** (test suites, type checkers, linters)

### 18.3 The "Stone Soup" Attribution Problem

In agentic systems, massive human labor (writing specs, designing harnesses, monitoring output, fixing errors) gets misattributed to AI capability. Huntley's caveat -- "There is no way this is possible without senior expertise guiding Ralph" -- is the honest version.

### 18.4 Limited Applicability Beyond Coding

Coding is the ideal domain because of the deterministic-probabilistic pairing: write code (probabilistic), run compiler/tests (deterministic), iterate. Most human activities don't have this structure.

### 18.5 Greenfield Bias

Many impressive results are greenfield projects. For brownfield work: the agent must understand existing architecture, tests may be incomplete, modifications must respect implicit conventions, risk of breaking existing functionality is much higher.

### 18.6 When NOT to Use Harness Engineering

- **Simple one-shot tasks**: Harness adds overhead without benefit
- **Domains without deterministic verification**: Feedback loop collapses
- **When human review is faster**: Overhead of specifying, monitoring, correcting may exceed manual cost
- **Security-critical operations without proper isolation**: Risk outweighs productivity gain
- **When the codebase has low harnessability** (per Fowler): Weakly-typed, poorly-structured legacy code with no tests

### 18.7 The Scale Confusion

| Approach | Complexity | Best For |
|----------|-----------|----------|
| Ralph/bash loop | ~10 lines | Single developer, greenfield, rapid iteration |
| Generator-Evaluator | ~100s of lines | Quality-critical features, multi-session work |
| Full orchestration (LangGraph, etc.) | ~1000s of lines | Enterprise, multi-agent, production systems |
| 8-layer reference architecture | Aspirational | No public implementation covers all 8 layers |

Choose the simplest approach that meets your actual needs.

### 10.2 Task Sizing Research

**Source: METR (Model Evaluation & Threat Research)**, "Measuring AI Ability to Complete Long Tasks" (March 2025):
- **AI task duration doubles every ~7 months** (capability growth). Updated Time Horizon 1.1 model (January 2026) suggests the rate has accelerated to ~4.3 months.
- **95% per-step reliability yields only 36% over 20 steps** (compound failure math)
- **Doubling task duration quadruples failure rate**

**Source: Toby Ord** (arXiv:2505.05115, "Is there a Half-Life for the Success Rates of AI Agents?", May 2025):
- AI agent failure follows a constant hazard rate analogous to radioactive decay.
- Claude 3.7 Sonnet achieves 50% success on tasks up to 59 minutes, but requires tasks under 15 minutes for 80% success.
- Every AI agent experienced degraded success rates as task duration increased.

**Practical implication**: Right-sized tasks should target 15-30 minutes of agent work per session. Multi-hour tasks must be decomposed into many such sessions.

## 15. Academic Research

### 15.1 Natural-Language Agent Harnesses (NLAHs)
**URL**: https://arxiv.org/html/2603.25723v1 (March 2026)

Externalizes harness control logic as portable, editable natural-language artifacts rather than scattering it across controller code.

**NLAH components**: Contracts (I/O constraints), Roles (solver/verifier/researcher), Stage Structure (plan -> execute -> verify -> repair), Adapters (deterministic hooks), State Semantics (what persists), Failure Taxonomy.

**Key ablation results**:
- Self-evolution module: +4.8% (SWE-bench)
- File-backed state: +1.6% (SWE), +5.5% (OSWorld)
- Verifier: **-0.8% (SWE)** -- can add overhead without guaranteed gains
- Multi-candidate search: **-2.4% (SWE)** -- also negative

**Key finding**: "More structure doesn't automatically improve performance when intermediate acceptance criteria diverge from final benchmarks."

### 15.2 Meta-Harness: End-to-End Optimization
**URL**: https://arxiv.org/abs/2603.28052 (March 2026)

An outer-loop system that searches over harness code using an agentic proposer with filesystem access to all prior candidates' source code, scores, and execution traces.

**Results**: +7.7 points over SOTA context management with 4x fewer tokens; +4.7 points on 200 IMO-level problems.

**Relevance**: Harness configurations can be systematically optimized rather than hand-tuned. Suggests an approach to A/B testing harness configurations.

### 15.3 AutoHarness: Automatic Constraint Enforcement
**URL**: https://arxiv.org/abs/2603.03329 (February 2026)

LLMs automatically generate constraint-enforcement harnesses through iterative refinement with environment feedback.

**Key results**:
- Smaller model (Gemini-2.5-Flash) with synthesized harness outperformed larger model (Gemini-2.5-Pro) without one
- The harness **prevents** illegal moves (proactive constraint enforcement), rather than "eliminates" them retroactively

### 15.6 ACRFence: Checkpoint-Restore Security
**URL**: https://arxiv.org/abs/2603.20625 (March 2026)

Identifies a novel threat model for LLM agent checkpoint-restore: agents re-synthesize subtly different requests after restore. Two attack classes: Action Replay and Authority Resurrection. Proposed solution: ACRFence records irreversible tool effects and enforces replay-or-fork semantics.

**Directly relevant to multi-hour harness systems** that need checkpointing and recovery.
