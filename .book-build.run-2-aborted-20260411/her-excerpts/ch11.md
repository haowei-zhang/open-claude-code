## From §5: Pattern 11 Single-Purpose Tool Design

11. **Single-Purpose Tool Design**: FileReadTool, FileEditTool, GrepTool each with individual permission rules

This pattern advocates for designing tools that do exactly one thing, with a clear and narrow scope. Rather than a single "FileTool" that can read, write, search, and modify files, the harness provides separate tools for each operation:

- **FileReadTool**: Reads file contents. Permission: typically always allowed.
- **FileEditTool**: Modifies file contents. Permission: requires approval for each edit.
- **GrepTool**: Searches file contents. Permission: typically always allowed.
- **BashTool**: Executes shell commands. Permission: high-risk, requires approval.

**Key benefits**:
- **Fine-grained permission control**: Each tool has its own permission policy. Read operations can be automatically approved; write operations require human confirmation.
- **Clearer model behavior**: The model sees separate tools and must explicitly choose which operation to perform, reducing ambiguity about intent.
- **Easier security auditing**: When each tool has a single purpose, it's straightforward to audit what kinds of operations the agent is performing and detect anomalous patterns.
- **Reduced tool description complexity**: A tool that does one thing has a simple, unambiguous description. The model is less likely to misuse a single-purpose tool than a multi-purpose one.

This pattern directly combats the "Tool Explosion" failure mode (6.8) -- not by reducing the number of tools, but by making each tool's purpose and permissions crystal clear.

## From §4: Fowler Computational vs Inferential

### 4.2 Execution Types

- **Computational Controls**: Deterministic, fast (milliseconds). Tests, linters, type checkers. Reliable but limited scope.
- **Inferential Controls**: AI-powered semantic analysis. Slower, non-deterministic, but richer for complex judgments.

The distinction between computational and inferential controls is critical for harness design:

**Computational controls** are the backbone of the harness's quality gates. They are deterministic, fast, and reliable -- but they can only check what can be formally specified. A type checker can verify that types are correct; a linter can verify that code follows style rules; a test suite can verify that specific behaviors are present. They cannot judge code quality, design elegance, or whether a solution is "good enough."

**Inferential controls** fill the gaps that computational controls cannot reach. An LLM-based evaluator can judge design quality, architectural coherence, and user experience -- but at the cost of non-determinism and slower execution. The evaluator may give different scores on different runs, and its judgment may be wrong.

The optimal harness uses both: computational controls as the primary quality gate (fast, deterministic, reliable), with inferential controls reserved for judgments that computational tools cannot make (design quality, subjective criteria).
