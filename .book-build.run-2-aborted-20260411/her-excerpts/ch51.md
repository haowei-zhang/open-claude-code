### 14.2 The Observability Gap

Agents fail silently because their response format looks correct. A 200 OK from a tool call doesn't mean the operation succeeded semantically. Observability must go beyond "did the API call return?" to "did the operation achieve its intended effect?"

### 6.6 Silent Failures
- **Symptom**: Agent proceeds after tool errors as if successful
- **Fix**: Structured output validation after every tool call

(From Section 6 Failure Modes and Recovery Patterns)

The observability gap and silent failures are two sides of the same coin. The agent reports success (200 OK, no error output) but the operation failed semantically. Without structured output validation after every tool call, the agent proceeds on a broken foundation. The observability gap means that even external monitoring cannot detect these failures because the response format looks correct.

From Section 14.1 Three Pillars for Agent Observability:
- **Traces**: Distributed tracing across multi-agent workflows. Each tool call, sub-agent dispatch, and model invocation is a span.
- **Metrics**: Per-session and per-task metrics including token usage, cost accrual rate, tool call latency and success rates, task completion rate, context window utilization
- **Logs**: Structured logging of agent decisions, tool call parameters/results, and state transitions. Critical for post-hoc debugging of "why did the agent do X?"

From Section 14.4 Alerting Patterns:
- **Staleness**: No progress file update or git commit for N minutes
- **Quality degradation**: Evaluator scores drop below threshold for N consecutive evaluations

The fix for silent failures requires bridging the observability gap: structured output validation after every tool call, combined with semantic observability that checks whether the operation achieved its intended effect, not just whether it returned without error.
