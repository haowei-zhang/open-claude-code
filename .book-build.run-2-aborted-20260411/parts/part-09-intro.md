# Part IX: Observability, Cost, and Security

A system that cannot be observed cannot be trusted. A system whose costs are invisible cannot be managed. A system whose attack surface is unmapped cannot be defended. Part IX addresses the three pillars of production readiness that separate a research prototype from a deployable product: observability, cost accounting, and security.

These three chapters are grouped together because they represent the non-functional requirements that most agent implementations defer—and that most agent failures trace back to. The harness engineering research documented in HER Section 14 (Observability), Section 13 (Cost Management), and Section 12 (Guardrails) identifies these concerns as the most consistently under-invested areas in agent system design. The chapters in this part show how cc implements each one, where it succeeds, and where gaps remain.

Observability in an agent system is harder than in a traditional service. The internal state of a language model is opaque; the chain of reasoning that produced a tool call is not directly inspectable. What can be observed are the inputs, outputs, timing, and side effects of each step. Chapter 50 covers cc's analytics pipeline—its sink abstraction, Datadog integration, GrowthBook feature flags, the tengu_* event taxonomy, and the cost tracker that records token consumption across every request. The chapter also addresses PII handling, a concern that becomes acute when every tool invocation and model response is potentially logged.

Cost tracking is inseparable from observability but deserves its own focus because the economics of language model calls are unlike the economics of traditional compute. A single agent session can burn through millions of tokens; a misconfigured loop can generate costs that spiral without any visible failure. The cost tracker and kill-switch mechanisms described in Chapter 50 are the financial equivalent of circuit breakers, and their design carries lessons for any team building on metered API services.

Debugging and diagnostics, covered in Chapter 51, are the other side of the observability coin. When something goes wrong—and in agent systems, something always goes wrong—the developer needs structured logs, diagnostic screens, and a doctor command that can verify the health of every subsystem. The chapter traces cc's logging layers from verbose debug output through structured diagnostic records to the interactive doctor screen, and examines how silent failures (one of HER's documented failure modes) are detected and surfaced.

Security, covered in Chapter 52, is where all of the preceding material converges. The threat model chapter walks through HER Section 12's five-layer defense-in-depth and maps each layer to cc's concrete defenses. Prompt injection, supply-chain attacks via MCP servers and skills, system-prompt leakage, data exfiltration through tool outputs, and checkpoint-restore side effects are each analyzed with reference to specific code paths. This chapter is the most cross-referential in the book, drawing on every prior part: tool dispatch (Part III), permission models (Part VI), hook pipelines (Part VI), MCP transport (Part VII), and remote agent bindings (Part VIII).

Chapter 50, Analytics, Cost Tracking, and GrowthBook, details the event pipeline from tool invocation through sink delivery, the feature-flag system that gates new functionality, and the cost accounting that tracks token spend across sessions. Chapter 51, Debug Logs, Diagnostics, and Doctor, examines the logging architecture, diagnostic record types, the doctor health-check screen, and the security review command. Chapter 52, Threat Model: CC Through the Lens of HER Section 12, maps HER's five-layer defense model onto cc's implementation, covering prompt injection, supply-chain risks, data leakage, and checkpoint-restore hazards with concrete file-path evidence.

By the end of this part, the reader should understand how cc makes its internal state visible, how it tracks and bounds the financial cost of language model calls, and how it defends against the attack vectors that HER identifies as most critical. These three capabilities—see, budget, and protect—are the load-bearing walls of any production agent. Without them, no amount of clever prompting or tool design can produce a system worthy of trust.
