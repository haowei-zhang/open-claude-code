# HER Excerpts for Chapter 12: Tool Dispatch Pipeline

## §5 Pattern 12 — Deterministic Lifecycle Hooks

**Deterministic Lifecycle Hooks**: Shell commands at 25+ lifecycle points (PreToolUse, PostToolUse, SessionStart, etc.)

Lifecycle hooks are deterministic shell commands that run at defined points in the agent's execution. They are not model-generated -- they are user-specified, deterministic, and always execute. Key properties:

- **Deterministic**: Same input always produces the same behavior (unlike model-generated decisions)
- **Blocking**: The pipeline waits for hook completion before proceeding
- **Exit-code semantics**: Non-zero exit can block the action, modify the input, or log a warning
- **Composable**: Multiple hooks can chain at the same lifecycle point

Hook types include: command hooks (shell execution), prompt hooks (modify the prompt), HTTP hooks (call external services), agent hooks (invoke sub-agents), and function hooks (in-process TypeScript).

## §6.8 — Tool Explosion

- **Symptom**: Too many tools degrade selection accuracy
- **Fix**: Progressive tool expansion starting with <20

When an agent has too many tools available simultaneously, it struggles to select the right one. Tool descriptions consume context window space, and the model's tool-selection accuracy degrades as the tool count increases. The HumanLayer blog notes that "too many tools is bad" -- excess tool descriptions push agents into "the dumb zone" faster.

The dispatch pipeline must manage tool visibility. Not all registered tools should be presented to the model in every query. Progressive tool expansion (Pattern 9) ensures only the most relevant subset is active at any time.

## §6.6 — Silent Failures

- **Symptom**: Agent proceeds after tool errors as if successful
- **Fix**: Structured output validation after every tool call

Silent failures are particularly dangerous in the dispatch pipeline because the model treats tool output at face value. If a tool returns an error but the model interprets it as success, the agent continues on a corrupted foundation. The harness must:

- Validate all tool outputs against expected schemas
- Surface errors explicitly in the tool result format
- Prevent the model from interpreting error messages as successful output
- Implement structured error types that the model cannot easily misinterpret
