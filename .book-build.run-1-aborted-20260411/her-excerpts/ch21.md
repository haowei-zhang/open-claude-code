# HER Excerpts for Chapter 21: Multi-Agent Coordinator: The Swarm Layer

## §9.2 — Generator-Evaluator Pattern and the Ouroboros Problem

The most universally recommended pattern across all sources:

```
Generator Agent --writes--> Artifact --evaluated-by--> Evaluator Agent
     ^                                                        |
     |                                                        |
     +------- feedback (specific, actionable) ----------------+
```

**Evaluator design principles**:
- Fresh context window (no knowledge of generation process)
- Specific gradable criteria with clear definitions
- Few-shot examples for each quality level
- Hard thresholds (not soft suggestions)
- Weight toward known model weak points
- The evaluator tests like a real user would (browser automation, not code inspection)

**The Ouroboros Problem**: When both generator and evaluator are LLMs, who validates the validator? If the evaluator hallucinates approval, the feedback loop amplifies rather than corrects errors. Mitigations:
- Use **deterministic sensors** (tests, linters, type checkers) as the primary quality gate; use LLM evaluators only for semantic/subjective judgments that deterministic tools cannot assess.
- **Ground evaluator output in observable artifacts** -- e.g., the evaluator must cite specific test results, specific lines of code, or specific browser screenshots rather than making unsubstantiated quality claims.
- The NLAH paper's ablation data is cautionary: adding a verifier produced **-0.8% on SWE-bench** -- the verifier hurt rather than helped when its acceptance criteria diverged from the actual benchmark.

## §9.3 — Agent Communication (File-Based)

**File-based communication** is preferred over programmatic handoffs:
- One agent writes a structured file
- Another agent reads it in a fresh context
- Maintains context fidelity better than passing state through code
- Git provides audit trail and rollback capability

**Security caution**: File-based communication persists data to disk. Without cleanup protocols, sensitive data can leak between sessions or between agents working on unrelated tasks. Use ephemeral directories and explicit cleanup for sensitive operations.

## §5 Pattern 8 — Fork-Join Parallelism

**Fork-Join Parallelism**: Multiple subagents in isolated git worktrees; cached parent context reuse

The fork-join pattern enables parallel execution of independent tasks:
1. **Fork**: The parent agent spawns multiple sub-agents, each in its own isolated worktree with a cached copy of the parent's context
2. **Execute**: Sub-agents work in parallel on independent tasks without interfering with each other
3. **Join**: Results from all sub-agents are merged back into the parent's context

The swarm coordinator implements this pattern at scale: it manages the full lifecycle of multiple parallel agents, routes messages between them, and handles the join semantics when results must be consolidated.
