# HER Excerpts for Chapter 20: Agent Definitions: Loading, Frontmatter, and Built-Ins

## §7.4 — Sub-agents Configuration Surface

Sub-Agents (Context Firewalls):
- Discrete tasks in isolated context windows
- Use expensive models (Opus) for parent orchestration
- Use cheaper models (Sonnet, Haiku) for sub-tasks
- Primary benefit: prevents research/exploration from consuming the main context window

Agent definitions -- the Markdown + YAML frontmatter files that describe each agent's capabilities, constraints, and invocation rules -- are a configuration surface. They determine:

- Which tools the agent has access to
- What model tier it uses
- Whether it runs in isolation or shares context
- How its output is formatted and returned to the parent

The frontmatter contract is the interface between the harness's configuration surface and the agent's runtime behavior. Changes to frontmatter fields directly control the agent's capabilities without modifying code.

## §5 Pattern 2 — Scoped Context Assembly

**Scoped Context Assembly**: Multi-level instruction loading (org -> user -> project -> directory)

Agent definitions are loaded at multiple scope levels, analogous to the CLAUDE.md loading cascade:

- **Built-in agents**: Shipped with the product, always available
- **Plugin agents**: Installed via MCP or skill directories, available when the plugin is active
- **User-defined agents**: Stored in `~/.claude/agents/`, personalized per developer
- **Project agents**: Stored in `.claude/agents/` within a project, project-specific

More specific scopes override or supplement broader ones, following the same precedence rules as the settings cascade. This ensures that project-specific agent definitions take precedence over user-level ones, which take precedence over built-ins.
