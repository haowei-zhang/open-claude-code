# HER Excerpts for Chapter 11: Anatomy of a Tool: `Tool.ts`, `buildTool`, and the Base Type

## §5 Pattern 11 — Single-Purpose Tool Design

**Single-Purpose Tool Design**: FileReadTool, FileEditTool, GrepTool each with individual permission rules

Each tool has a single, well-defined responsibility. Rather than a monolithic "file operations" tool, the harness provides separate tools for reading, writing, editing, searching, and globbing. This enables:

- **Granular permission control**: Each tool can be individually allowed, denied, or gated behind user approval
- **Clear failure boundaries**: When a tool fails, the failure is isolated to its specific operation
- **Targeted risk classification**: Dangerous operations (write, edit) can have stricter approval requirements than safe ones (read, grep)
- **Independent evolution**: Tools can be modified, added, or removed without affecting others

The alternative -- a single "filesystem" tool with sub-commands -- makes permission gating coarser and failure modes harder to isolate.

## §4 — Fowler: Computational vs Inferential

### Execution Types

- **Computational Controls**: Deterministic, fast (milliseconds). Tests, linters, type checkers. Reliable but limited scope.
- **Inferential Controls**: AI-powered semantic analysis. Slower, non-deterministic, but richer for complex judgments.

This distinction maps directly to tool design. A tool like `FileReadTool` is computational: its output is deterministic and verifiable. A tool like `WebFetchTool` straddles the boundary: the HTTP request is computational, but the content it returns may require inferential processing. The harness must treat computational and inferential tool outputs differently -- computational outputs can be trusted at face value; inferential outputs require validation.
