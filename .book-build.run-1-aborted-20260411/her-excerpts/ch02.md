## §5 — The 12 Agentic Harness Patterns (Index)

Source: [12 Agentic Harness Patterns from Claude Code](https://generativeprogrammer.com/p/12-agentic-harness-patterns-from)

**Important caveat**: These patterns are derived from reverse-engineering Claude Code's architecture. They represent implementation decisions of one specific product (CLI-first, Anthropic-native). Other platforms make fundamentally different tradeoffs.

### Memory and Context (5 patterns)

1. **Persistent Instruction File**: CLAUDE.md auto-loaded at session start
2. **Scoped Context Assembly**: Multi-level instruction loading (org -> user -> project -> directory)
3. **Tiered Memory**: Compact index (200 lines max) always in context; topic files on demand; full transcripts on disk
4. **Dream Consolidation**: Background processes review, deduplicate, prune memory during idle time (8 phases, 5 compaction types)
5. **Progressive Context Compaction**: Four layers: HISTORY_SNIP, Microcompact, CONTEXT_COLLAPSE, Autocompact

### Workflow and Orchestration (3 patterns)

6. **Explore-Plan-Act Loop**: Three phases with escalating permissions (read-only -> discussion -> full access)
7. **Context-Isolated Subagents**: Separate context windows per phase; research agents cannot edit
8. **Fork-Join Parallelism**: Multiple subagents in isolated git worktrees; cached parent context reuse

### Tools and Permissions (3 patterns)

9. **Progressive Tool Expansion**: Start with <20 tools; activate more on demand (not all 60+ at once)
10. **Command Risk Classification**: Deterministic pre-parsing and per-tool permission gating
11. **Single-Purpose Tool Design**: FileReadTool, FileEditTool, GrepTool each with individual permission rules

### Automation (1 pattern)

12. **Deterministic Lifecycle Hooks**: Shell commands at 25+ lifecycle points (PreToolUse, PostToolUse, SessionStart, etc.)

## §6 — The 17 Failure Modes (Index)

| # | Failure Mode | Symptom | Fix |
|---|-------------|---------|-----|
| 6.1 | Context Rot | Performance degrades 30%+ when key content falls in mid-window positions | Active context management (summarization, pruning, progress file) |
| 6.2 | Premature Completion | Agent declares work done too early | Comprehensive JSON feature list with all items initially marked "failing" |
| 6.3 | Self-Evaluation Bias | Agent rates own work too generously | Separate evaluator agent in a fresh context window |
| 6.4 | Placeholder Implementations | Agents default to stubs because compiling triggers reward signals | Explicit anti-placeholder instructions |
| 6.5 | Context Anxiety | Models prematurely wrap up near perceived context limits | Context resets with structured handoffs |
| 6.6 | Silent Failures | Agent proceeds after tool errors as if successful | Structured output validation after every tool call |
| 6.7 | Infinite Loops | Retry without progress | Maximum retry counts, exponential backoff, loop detection |
| 6.8 | Tool Explosion | Too many tools degrade selection accuracy | Progressive tool expansion starting with <20 |
| 6.9 | Compounding Bugs Across Sessions | New session builds on broken state | Baseline verification at session start |
| 6.10 | Yak Shaving / Scope Creep | Agent wanders into tangential fixes | Strict single-task-per-session constraint |
| 6.11 | Cost Explosion / Runaway Spending | Infinite loops or multi-agent chains rack up hundreds or thousands of dollars | Per-session and per-task cost caps; real-time token metering |
| 6.12 | Hallucinated Tool Calls | Agent fabricates tool parameters or calls wrong APIs | Schema validation on all tool call parameters |
| 6.13 | Security Vulnerabilities / Prompt Injection | Malicious content manipulates agent behavior | Input sanitization; output filtering; least-privilege tool permissions |
| 6.14 | Model Regression from Provider Updates | Harness behavior breaks silently when provider updates model | Regression test suite; pin model versions where stability matters |
| 6.15 | Data Leakage Between Contexts | Information leaks between sessions or sub-agents | Context isolation; cleanup protocols; ephemeral directories |
| 6.16 | Checkpoint-Restore Side Effects | Agents re-synthesize subtly different requests after restore | Record irreversible tool effects; enforce replay-or-fork semantics |
| 6.17 | Goal Misinterpretation / Specification Gaming | Agent optimizes for proxy metrics rather than actual intent | Explicit acceptance criteria; human checkpoint at 25% completion |

## §20 — Synthesized Best Practices (12 Core Principles)

1. **Context windows are the constraint; structured artifacts are the solution.**
2. **Separate generation from evaluation.** But be aware of the Ouroboros problem -- deterministic evaluation is more reliable than LLM evaluation.
3. **One task per session.** This single rule prevents more failures than almost anything else.
4. **Verify before building.** Always run a baseline check at session start.
5. **Wire in fast feedback loops.** Tests, linters, type checkers provide deterministic back-pressure.
6. **Repository is single source of truth.** All state must be persisted to files and git.
7. **Humans steer, agents execute.** Design explicit human-in-the-loop checkpoints for multi-hour tasks.
8. **Expect eventual consistency.** The speed of the loop matters more than perfection in any single iteration.
9. **Simplify relentlessly.** Strip unneeded harness complexity as models improve.
10. **Control costs actively.** Set per-session and per-task cost caps. Budget for 3-10x the happy-path cost.
11. **Observe everything.** Traces, metrics, and structured logs are table stakes for production use.
12. **Secure by default.** Treat all external content as untrusted. Use least-privilege permissions.
