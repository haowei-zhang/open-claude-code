# HER Excerpts for Chapter 44: Bridges: VS Code, JetBrains, and Web

## §9.1 — Local Orchestrators

**Local Orchestrators**: Separate processes coordinated by a parent (e.g., Ralph loop spawning multiple Claude instances)
- Process-level isolation, no shared state
- Communication via filesystem (files, git)
- Best for: parallel exploration, background tasks

IDE bridges are a form of local orchestration. The IDE (VS Code, JetBrains) runs as a separate process that coordinates with cc through a bridge protocol. The bridge:

1. Establishes a communication channel between the IDE and cc
2. Routes user actions from the IDE to cc (e.g., "explain this code", "fix this bug")
3. Routes cc's responses back to the IDE for display
4. Manages the lifecycle of the cc process

Unlike in-process sub-agents, the IDE bridge provides a richer interaction surface: syntax highlighting, diff views, inline suggestions, and integrated terminal. The tradeoff is higher latency and more complex coordination.

## §12.4 — Data Exfiltration via Bridge

**Data Exfiltration Through Tool Calls**: Agent sends sensitive data to external services via tool calls (API requests, file uploads, etc.).
- **Mitigation**: Allowlist external endpoints; monitor tool call parameters for sensitive data patterns; require human approval for external communications.

IDE bridges create a new data exfiltration vector. The bridge transports data between the IDE and cc, which means:

- **Inbound attachments**: Files from the IDE pass through the bridge into cc's context. These must be validated and sanitized.
- **Outbound data**: cc's responses pass through the bridge to the IDE. If the bridge connects to a remote IDE (web-based), this data traverses the network.
- **Trusted devices**: The bridge protocol must authenticate the IDE to prevent unauthorized connections from exfiltrating data.

The harness must treat the bridge as an untrusted channel: encrypt all bridge traffic, authenticate both endpoints, and validate all data passing through the bridge.
