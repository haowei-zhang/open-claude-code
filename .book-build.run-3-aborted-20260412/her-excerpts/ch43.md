### §11 Human-in-the-Loop

## 11. Human-in-the-Loop Design Patterns

The canonical sources state "Humans steer, agents execute" but rarely detail the specific patterns for how humans participate in agent workflows. For multi-hour tasks, these patterns are essential.

### 11.1 Confidence-Based Routing
- **Above threshold** (e.g., 90% confidence): Agent proceeds autonomously
- **Below threshold**: Agent queues the decision for human approval, continues with other work
- **Implementation**: The agent reports its confidence and reasoning; a routing layer (which can be deterministic or model-based) decides whether to proceed or escalate

### 11.2 Tiered Escalation
- **Tier 1** (automated): Deterministic checks handle (linting, testing, formatting)
- **Tier 2** (agent self-correction): Agent gets feedback from Tier 1 and tries again
- **Tier 3** (human front-line): Moderate-risk decisions (e.g., "should I refactor this module?")
- **Tier 4** (human expert): High-risk decisions (architecture changes, security-sensitive operations, production deployments)

### 11.3 Async Approval
- Agent parks a blocked action, records context about what it tried and why it's uncertain
- Agent continues with non-blocked work
- When human approves/denies, agent resumes the blocked work path
- **Critical for multi-hour tasks**: The agent should never fully block on human input. Always have a queue of independent tasks to work on while waiting.

### 11.4 Context-Rich Escalation
When the agent escalates to a human, it must provide:
- What it was trying to do
- What it tried
- Why it failed or is uncertain
- What options it sees
- What it recommends (if it has a preference)

This prevents the human from having to reconstruct full context from scratch.

### 11.5 Handoff Protocols
- **Full context transfer**: Agent writes a structured handoff document summarizing current state, what's done, what's remaining, and any open questions
- **Incremental review**: Human reviews completed chunks (e.g., every 3 tasks) rather than waiting for the end
- **Checkpoint review**: Mandatory human review at 25% and 75% of task completion to catch goal misinterpretation early

### §7 Configuration Surfaces

## 7. Configuration Surfaces

Source: [HumanLayer: Skill Issue -- Harness Engineering for Coding Agents](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents)

Six configuration surfaces compose a modern harness:

### 7.1 CLAUDE.md / AGENTS.md / .cursor/rules Files
- Deterministically injected into system prompt every session
- Keep under 60 lines for optimal performance

- **ETH Zurich study** (arXiv:2602.11988, "Evaluating AGENTS.md"): This paper found that **context files tend to reduce task success rates compared to providing no repository context, while also increasing inference cost by over 20%.** This applies to both LLM-generated and developer-committed context files. The paper recommends describing only "minimal requirements" -- verbose instructions and detailed directory trees hurt rather than help.

  **Implication**: More instruction is not always better. The harness should provide minimal, targeted context rather than comprehensive documentation dumps. This finding challenges the common assumption that detailed AGENTS.md files improve agent performance.

- Three-part structure recommended (if used): WHY (project context) / WHAT (conventions) / HOW (workflows)

### 7.2 MCP Servers
- Extend capabilities with external tool access
- "Too many tools is bad" -- excess tool descriptions push agents into "the dumb zone" faster
- If an MCP server duplicates CLI functionality well-represented in training data, use the CLI instead
- **Security note**: MCP servers are a supply chain attack surface. Treat them like untrusted npm packages.

### 7.3 Skills (Progressive Disclosure)
- Agents access specific instructions/tools only when contextually needed
- Treat skills like untrusted npm packages (security risk)
- Reduces cognitive load by not front-loading all instructions

### 7.4 Sub-Agents (Context Firewalls)
- Discrete tasks in isolated context windows
- Use expensive models (Opus) for parent orchestration
- Use cheaper models (Sonnet, Haiku) for sub-tasks
- Primary benefit: prevents research/exploration from consuming the main context window

### 7.5 Hooks (Lifecycle Events)
- User-defined commands at lifecycle events (PreToolUse, PostToolUse, Stop, etc.)
- Common patterns:
  - Auto-format after file edits
  - File protection via PreToolUse
  - Premature-completion prevention via Stop hooks
  - Quality gates via TaskCompleted hooks

### 7.6 Back-Pressure Mechanisms
- "Swallow the output and only surface errors"
- Success is silent; only failures produce verbose output
- Running full test suites floods context and causes task loss
- Key principle: only feed back what requires agent action

**Key finding**: "The next time your coding agent isn't performing the way you expect, before you blame the model, check the harness. The model is probably fine. It's just a skill issue."
