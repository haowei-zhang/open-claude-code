### §10 Session Protocol (ORIENT/SETUP)

## 10. Task Decomposition and Session Design

### 10.1 The One-Task-Per-Session Rule

This is the single most impactful rule across all sources. It prevents:
- Context exhaustion mid-feature
- Scope creep and yak shaving
- Compounding errors
- Lost progress due to context resets

### 10.2 Task Sizing Research

**Source: METR (Model Evaluation & Threat Research)**, "Measuring AI Ability to Complete Long Tasks" (March 2025):
- **AI task duration doubles every ~7 months** (capability growth). Updated Time Horizon 1.1 model (January 2026) suggests the rate has accelerated to ~4.3 months.
- **95% per-step reliability yields only 36% over 20 steps** (compound failure math)
- **Doubling task duration quadruples failure rate**

**Source: Toby Ord** (arXiv:2505.05115, "Is there a Half-Life for the Success Rates of AI Agents?", May 2025):
- Building on METR's data, Ord found that AI agent failure follows a constant hazard rate analogous to radioactive decay.
- Claude 3.7 Sonnet achieves 50% success on tasks up to 59 minutes of human-equivalent time, but requires tasks under 15 minutes for 80% success.
- **General finding**: Every AI agent in the dataset experienced degraded success rates as task duration increased, with the decline starting in the 15-60 minute range depending on the model and harness.
- **Note**: Ord later acknowledged that further analysis shows agents don't perfectly obey a constant hazard rate -- they have a declining hazard rate as tasks progress, complicating the simple half-life model.

**Practical implication for multi-hour tasks**: Right-sized tasks should target 15-30 minutes of agent work per session. Multi-hour tasks must be decomposed into many such sessions, with state handoffs between them.

### 10.3 Session Protocol

Synthesized across Anthropic, OpenAI, and practitioner sources:

```
1. ORIENT     -- Read workspace state (pwd, git log, progress file)
2. SETUP      -- Run init script, install dependencies if needed
3. VERIFY     -- Run baseline tests/checks (CRITICAL: before any new work)
4. SELECT     -- Pick exactly one task from the task list
5. IMPLEMENT  -- Write code with frequent git commits
6. TEST       -- Run tests, lint, type-check (automated back-pressure)
7. UPDATE     -- Update task list status, progress notes, git commit
8. EXIT       -- Clean exit with state fully persisted
```

### 10.4 JSON Task List Format

```json
{
  "category": "Authentication",
  "id": "auth-001",
  "description": "Implement OAuth2 login flow",
  "steps": [
    "Create OAuth2 callback endpoint",
    "Handle token exchange",
    "Store refresh tokens securely",
    "Add session management"
  ],
  "passes": false,
  "notes": ""
}
```

**Constraints**:
- Tasks are append-only (never delete, only mark as done)
- Only the `passes` and `notes` fields may be modified
- Task descriptions are immutable once created
- Boolean `passes` field prevents ambiguous "partial" states

### 10.5 Greenfield vs. Brownfield

A critical distinction the canonical sources often understate:

- **Greenfield** (new codebase): All canonical sources' patterns apply. Ralph is explicitly greenfield-only. The agent has maximum freedom and minimal legacy constraints.
- **Brownfield** (existing codebase): Significantly harder. The agent must understand existing architecture, conventions, and implicit constraints. Key adaptations needed:
  - Extended ORIENT phase to map existing architecture
  - Stricter scope constraints (touching unfamiliar code is riskier)
  - More conservative testing (existing tests as regression baseline)
  - Higher human oversight for architectural decisions
  - Fowler's "harnessability" concept is most relevant here

### §12 TLS/mTLS defense in depth

## 12. Guardrails, Safety, and Security

### 12.1 Five-Layer Defense-in-Depth

From the academic paper "Building AI Coding Agents for the Terminal":

1. **Prompt-level guardrails**: Instructions in system prompt about what not to do
2. **Schema-level restrictions**: Tool parameter validation, allowlists
3. **Runtime approval system**: Human-in-the-loop for destructive operations
4. **Tool-level validation**: Per-tool safety checks before execution
5. **Lifecycle hooks**: Deterministic shell commands at lifecycle events

### 12.2 GUARDRAILS.md Protocol

Source: https://guardrails.md/

Uses a **Sign** structure:
- **Trigger**: When this guardrail activates
- **Instruction**: What the agent must do
- **Reason**: Why this guardrail exists
- **Provenance**: Who added it and when

### 12.3 Four Universal Safety Patterns

1. **Artifact Verification**: Check that generated outputs meet structural requirements before proceeding
2. **Context Rotation**: Periodically reset context to prevent degradation-induced errors
3. **Privilege Boundaries**: Different agents have different permission levels (research agents can't edit)
4. **Rate Limiting**: Prevent runaway loops and excessive API/tool usage

### 12.4 Security Threat Model for Agent Systems

This is a critical gap in most harness literature. For production multi-hour systems, the following threats must be addressed:

**Indirect Prompt Injection**: Malicious instructions embedded in files, tool outputs, web pages, or database records that the agent processes. The agent follows these injected instructions because it cannot reliably distinguish them from legitimate context.
- **Mitigation**: Input sanitization on all external content; treat file contents and tool outputs as untrusted; use deterministic validation (not LLM judgment) for security-critical decisions.

**Supply Chain Attacks via MCP Servers/Skills**: Compromised or malicious tools that the agent calls can exfiltrate data, modify behavior, or escalate privileges.
- **Mitigation**: Vet all MCP servers; restrict tool permissions to minimum required; audit tool call logs; run tools in sandboxed environments when possible.

**System Prompt Leakage**: Agent may be tricked into revealing its system prompt, harness configuration, or internal tool descriptions.
- **Mitigation**: Minimize sensitive information in system prompts; use post-processing filters on agent output.

**Data Exfiltration Through Tool Calls**: Agent sends sensitive data to external services via tool calls (API requests, file uploads, etc.).
- **Mitigation**: Allowlist external endpoints; monitor tool call parameters for sensitive data patterns; require human approval for external communications.

**Checkpoint-Restore Attacks** (ACRFence, arXiv:2603.20625): LLM agents re-synthesize subtly different requests after checkpoint-restore, causing duplicate payments, unauthorized credential reuse, and irreversible side effects. Two attack classes: Action Replay (replaying previously completed actions) and Authority Resurrection (reusing expired credentials).
- **Mitigation**: Record irreversible tool effects; enforce replay-or-fork semantics; use idempotency keys for all external operations.

### 12.5 The OpenClaw Incident

A cautionary real-world case: OpenClaw (an open-source agent framework) had 135,000 GitHub stars and 21,000 exposed instances when CVE-2025-53773 (CVSS 9.6) was discovered. The vulnerability allowed remote code execution through the agent's tool interface. This demonstrates that agent security is not theoretical -- it is an active, high-severity concern.

### 12.6 Idempotency for External Operations

For multi-hour tasks that interact with external systems (APIs, databases, email, payment systems), every external operation should be idempotent:
- Generate a unique operation ID before each external call
- Check whether the operation has already been performed before executing
- Store operation results mapped to their IDs
- On retry or restore, check the ID first -- if already completed, return the stored result

This prevents the most dangerous class of checkpoint-restore failures: duplicate side effects.
