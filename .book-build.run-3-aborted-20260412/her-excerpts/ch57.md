### §18 Limitations

## 18. Limitations, Skeptical Perspectives, and When NOT to Use

### 18.1 Is This Just DevOps Rebranded?

Muhammad Raza maps harness components directly to DevOps equivalents. The mapping is instructive:

| Harness Concept | DevOps Equivalent |
|----------------|-------------------|
| Execution environments | CI job runners (Docker, Firecracker) |
| Tool definitions | API design and permission scoping |
| Control loops | Health checks, deployment rollback |
| Guardrails | IAM policies, network rules, resource quotas |
| Observability | Structured logging, request tracing |
| Session management | Container lifecycle management |

**Assessment**: Harness engineering IS substantially DevOps applied to a new workload type. The core innovation is the *probabilistic* nature of the workload -- DevOps orchestrates deterministic processes, while harness engineering orchestrates a non-deterministic process (the LLM) that requires fundamentally different error handling (retry-and-hope rather than fix-the-bug). But the infrastructure patterns, the feedback loops, the observability requirements, and the cost management challenges are deeply familiar to anyone who's run production infrastructure.

Practitioners with DevOps backgrounds should recognize that their skills transfer directly. The discipline is not as novel as some framing suggests.

### 18.2 The Ouroboros Problem

When both generator and evaluator are LLMs, who validates the validator? The report recommends Generator-Evaluator as "the most universally recommended pattern" (Section 9.2), and it is -- but its limitations must be understood:

- An LLM evaluator can hallucinate approval just as easily as a generator can hallucinate success
- The NLAH paper's verifier ablation (-0.8% on SWE-bench) shows this is not theoretical
- **The strongest evaluators are deterministic** (test suites, type checkers, linters) -- use LLM evaluation only for judgments that deterministic tools cannot make

### 18.3 The "Stone Soup" Attribution Problem

Benjamin Riley (citing Alison Gopnik) raises a challenge: in agentic systems, massive human labor (writing specs, designing harnesses, monitoring output, fixing errors) gets misattributed to AI capability. OpenAI's "~1M lines, zero manually written" is technically true but obscures the human engineering effort that made it possible. Huntley's own caveat -- "There is no way this is possible without senior expertise guiding Ralph" -- is the honest version.

### 18.4 Limited Applicability Beyond Coding

Coding is the ideal domain for harness engineering because of the deterministic-probabilistic pairing: write code (probabilistic), run compiler/tests (deterministic), iterate. Most human activities don't have this structure. The patterns in this report should not be assumed to generalize to domains lacking strong deterministic verification (creative writing, strategic planning, research synthesis).

### 18.5 Greenfield Bias

Huntley explicitly states: "There's no way in heck would I use Ralph in an existing code base." Many of the report's most impressive results (OpenAI's ~1M lines, Huntley's $297 contract) are greenfield projects. For brownfield (existing codebase) work:
- The agent must understand existing architecture it didn't create
- Tests may be incomplete or absent, removing a key feedback mechanism
- Modifications must respect implicit conventions not captured in any document
- The risk of breaking existing functionality is much higher

### 18.6 When NOT to Use Harness Engineering

- **Simple one-shot tasks**: If the task fits in a single prompt/response, a harness adds overhead without benefit
- **Domains without deterministic verification**: If you can't automatically check the output, the feedback loop collapses and you're just running an LLM with extra steps
- **When human review is faster**: For tasks requiring deep domain expertise and judgment, the overhead of specifying, monitoring, and correcting an agent may exceed the cost of doing it manually
- **Security-critical operations without proper isolation**: If you cannot sandbox the agent's tool access, the risk of unintended side effects may outweigh the productivity gain
- **When the codebase has low harnessability** (per Fowler): Weakly-typed, poorly-structured legacy code with no tests is simultaneously where a harness is most needed and hardest to build

### 18.7 The Scale Confusion

The literature conflates harnesses operating at very different scales:

| Approach | Complexity | Best For |
|----------|-----------|----------|
| Ralph/bash loop | ~10 lines | Single developer, greenfield, rapid iteration |
| Generator-Evaluator | ~100s of lines | Quality-critical features, multi-session work |
| Full orchestration (LangGraph, etc.) | ~1000s of lines | Enterprise, multi-agent, production systems |
| 8-layer reference architecture | Aspirational | No public implementation covers all 8 layers |

These are qualitatively different systems, not points on a single continuum. Choose the simplest approach that meets your actual needs. Simon Willison's observation that a coding agent is fundamentally "a few dozen lines of code" is a useful reminder that complexity should be earned, not assumed.

### §10.2 METR

### 10.2 Task Sizing Research

**Source: METR (Model Evaluation & Threat Research)**, "Measuring AI Ability to Complete Long Tasks" (March 2025):
- **AI task duration doubles every ~7 months** (capability growth). Updated Time Horizon 1.1 model (January 2026) suggests the rate has accelerated to ~4.3 months.
- **95% per-step reliability yields only 36% over 20 steps** (compound failure math)
- **Doubling task duration quadruples failure rate**

**Source: Toby Ord** (arXiv:2505.05115, "Is there a Half-Life for the Success Rates of AI Agents?", May 2025):
- Building on METR's data, Ord found that AI agent failure follows a constant hazard rate analogous to radioactive decay.
- Claude 3.7 Sonnet achieves 50% success on tasks up to 59 minutes of human-equivalent time, but requires tasks under 15 minutes for 80% success.
- **General finding**: Every AI agent in the dataset experienced degraded success rates as task duration increased, with the decline starting in the 15-60 minute range depending on the model and harness.
- **Note**: Ord later acknowledged that further analysis shows agents don't perfectly obey a constant hazard rate -- they have a declining hazard rate as tasks progress, complicating the simple half-life model.

**Practical implication for multi-hour tasks**: Right-sized tasks should target 15-30 minutes of agent work per session. Multi-hour tasks must be decomposed into many such sessions, with state handoffs between them.


### §15 Academic Research (NLAH, Meta-Harness, AutoHarness, ACRFence)

## 15. Academic Research

### 15.1 Natural-Language Agent Harnesses (NLAHs)
**URL**: https://arxiv.org/html/2603.25723v1 (March 2026)

Externalizes harness control logic as portable, editable natural-language artifacts rather than scattering it across controller code.

**NLAH components**: Contracts (I/O constraints), Roles (solver/verifier/researcher), Stage Structure (plan -> execute -> verify -> repair), Adapters (deterministic hooks), State Semantics (what persists), Failure Taxonomy.

**Key ablation results**:
- Self-evolution module: +4.8% (SWE-bench)
- File-backed state: +1.6% (SWE), +5.5% (OSWorld)
- Verifier: **-0.8% (SWE)** -- can add overhead without guaranteed gains
- Multi-candidate search: **-2.4% (SWE)** -- also negative

**Key finding**: "More structure doesn't automatically improve performance when intermediate acceptance criteria diverge from final benchmarks." This is a crucial cautionary finding -- adding components (evaluators, verifiers, multi-candidate search) can make things worse.

### 15.2 Meta-Harness: End-to-End Optimization
**URL**: https://arxiv.org/abs/2603.28052 (March 2026)

An outer-loop system that searches over harness code using an agentic proposer with filesystem access to all prior candidates' source code, scores, and execution traces.

**Results**: +7.7 points over SOTA context management with 4x fewer tokens; +4.7 points on 200 IMO-level problems.

**Relevance to harness versioning**: This paper demonstrates that harness configurations can be systematically optimized rather than hand-tuned. For production systems, this suggests an approach to A/B testing harness configurations.

### 15.3 AutoHarness: Automatic Constraint Enforcement
**URL**: https://arxiv.org/abs/2603.03329 (February 2026)

LLMs automatically generate constraint-enforcement harnesses through iterative refinement with environment feedback.

**Key results**:
- Smaller model (Gemini-2.5-Flash) with synthesized harness outperformed larger model (Gemini-2.5-Pro) without one on broad benchmarks.
- The full "code-policy" version (a different method than the harness alone) outperformed GPT-5.2-High on **16 one-player TextArena games** specifically -- not across all benchmarks.
- The harness **prevents** illegal moves (proactive constraint enforcement), rather than "eliminates" them retroactively.

### 15.4 Building AI Coding Agents for the Terminal
**URL**: https://arxiv.org/html/2603.05344v1 (March 2026)

**Note**: This paper is about the OPENDEV system, not Claude Code specifically. The report cites it for general principles.

**Key distinction**:
- **Scaffolding** = assembly before first prompt (system prompt compilation, tool schema generation, subagent registration)
- **Harness** = runtime orchestration after assembly (tool dispatch, context management, safety enforcement, session persistence)

**Six-phase execution loop**: Pre-check/Compaction -> Thinking -> Self-Critique -> Action -> Tool Execution -> Post-Processing

### 15.5 Agent Reliability Science
**URL**: https://arxiv.org/html/2602.16666v1

**The capability-reliability gap**: Model development has shown small reliability improvements despite steady accuracy gains. Models get smarter but not necessarily more consistent. The "18 months" timeframe cited in some secondary sources is an interpretation, not a direct finding of the paper.

**Four reliability dimensions**: Consistency, Robustness, Predictability, Safety

### 15.6 ACRFence: Checkpoint-Restore Security
**URL**: https://arxiv.org/abs/2603.20625 (March 2026)
**Authors**: Yusheng Zheng, Yiwei Yang, Wei Zhang, Andi Quinn (UC Santa Cruz, University of Connecticut)

Identifies a novel threat model for LLM agent checkpoint-restore: agents re-synthesize subtly different requests after restore. Two attack classes: Action Replay (replaying completed actions) and Authority Resurrection (reusing expired credentials). Proposed solution: ACRFence records irreversible tool effects and enforces replay-or-fork semantics.

**Directly relevant to multi-hour harness systems** that need checkpointing and recovery.

### 15.7 Evaluating AGENTS.md (ETH Zurich)
**URL**: https://arxiv.org/abs/2602.11988

The paper found that **context files tend to reduce task success rates** compared to providing no repository context, while increasing inference cost by over 20%. This applies to both LLM-generated and developer-committed context files. Recommendation: describe only "minimal requirements."
